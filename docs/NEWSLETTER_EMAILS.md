# Graduate newsletter marketing broadcasts

New newsletters published through Admin → Manage Newsletters use Resend Marketing Broadcasts. The newsletter service never calls `/emails` or `/emails/batch`, including its connection check. Signup/password reset SMTP is separate and unchanged.

Only approved, non-rejected graduate brothers whose newsletter preference is enabled are queued. Addresses are deduplicated, with account email as a fallback when no contact email is entered. Existing newsletter posts are never backfilled. Each database batch becomes an isolated Resend segment and draft broadcast containing only its snapshot of graduate contacts. For large lists there can be multiple broadcasts for one issue. Each recipient receives a private message; addresses are not exposed to the browser or other contacts.

The integration checks existing Resend contacts and never resets `unsubscribed` to false. New contacts are created only if missing. Resend's `{{{RESEND_UNSUBSCRIBE_URL}}}` is included in HTML and plain text; Resend honors global marketing unsubscribes. Website preferences apply to future issues, and a website opt-in cannot override a prior Resend unsubscribe.

Required server-only secret: `RESEND_MARKETING_API_KEY`. The previous sending-only newsletter key cannot manage contacts, segments, and broadcasts. Resend currently exposes these capabilities through Full access keys; obtain explicit approval before creating/storing the new key. Never store credentials in source or client code. If the marketing key is absent, publication fails closed rather than falling back to transactional sends.

State in `newsletter_email_batches` records transport, segment ID, contact sync cursor, broadcast ID, and processing status. Draft broadcast IDs are saved before any send. Retries first retrieve the same broadcast and do not send it again once accepted. Lost draft-creation responses may leave an unused draft, but cannot cause duplicate sends. Isolated segments avoid mixing different newsletters' recipients. Legacy transactional campaigns are blocked from automatic retry.

Contact synchronization is paced at 600ms per provider call. The server processes for a bounded period and persists progress. While the publishing page remains open, the UI automatically continues pending work. Provider errors stop automatic continuation and expose Retry pending emails. Closing the page can leave unfinished work to resume manually. There is no scheduled background worker. Uncertain failures older than 23 hours require manual review in Resend. Admin counts represent recipient records processed, not inbox delivery; Resend can suppress unsubscribed contacts. Review marketing delivery metrics in Resend Broadcasts.

Connection check reads `/broadcasts?limit=1` and never creates a contact, campaign, or email. Deleting a website newsletter cannot recall a submitted broadcast. The Resend marketing plan/contact allowance is separate from transactional sending limits; this integration does not purchase or upgrade a plan.

Validation: 10 Node tests cover marketing-only endpoints, unsubscribe preservation, new-contact creation, draft-before-send persistence, retries, bounded progress, legacy blocking, admin authorization, configuration failure, and read-only connection checks. Database changes are tested in rolled-back transactions; no old or real newsletter is emailed during verification.
